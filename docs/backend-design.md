# Предложение по устройству собственного бэкенда

Статус: **на обсуждении**. Основание — [инвентаризация продукта](feature-inventory.md) и [интеграций](api-inventory.md). Стек и модель авторизации ещё не утверждены. Crowdfund служит образцом работы через PR; его архитектура не переносится автоматически.

## Требования, влияющие на архитектуру

Два клиента (web и admin), аккаунты с email/OAuth, сессии устройств, контент с изображениями, социальные связи, сообщения, уведомления и платёжные события требуют общего места для бизнес-правил и проверки прав. Нужны длительные соединения и фоновые операции; финансовые события, письма и загрузки должны корректно обрабатывать повторные попытки. Полный продукт реализуется небольшими PR.

## Расположение и разбиение

| Вариант | Выгода | Цена для этого проекта |
| --- | --- | --- |
| Вся логика внутри Next.js web | Меньше отдельных процессов, рядом с UI | Общий backend admin и web зависит от приложения web; фоновые задачи и соединения надо учитывать в модели хостинга |
| Отдельное приложение, модульный монолит | Единые правила для клиентов, транзакции в одной БД, независимый запуск сервера | Дополнительный процесс и конфигурация локального окружения |
| Несколько сервисов | Раздельное развёртывание и масштабирование доменов | Сетевые отказы, согласованность, наблюдаемость и инфраструктура усложняют каждую функцию |

**Рекомендация:** отдельное приложение `backend/` в текущем npm-монорепозитории, модульный монолит. Репозиторий и процесс сервера — разные границы. База общая; каждый модуль владеет своими данными, межмодульные операции проходят через явные функции. Для писем, обработки изображений и внешних событий предусмотреть фоновые задания; механизм и необходимость отдельного worker определить отдельно. Redis и брокер не добавлять без конкретного сценария.

## Серверный стек: варианты для выбора

| Вариант | Почему подходит | Что учитывать |
| --- | --- | --- |
| TypeScript + NestJS | Модули, dependency injection и единые conventions для большого набора доменов | Декораторы и дополнительные абстракции, необходимость понимать lifecycle framework |
| TypeScript + Fastify | Явные зависимости, инкапсуляция plugins, небольшой HTTP-слой | Организацию модулей и правила зависимостей нужно закрепить самим |
| Другой язык/стек | Возможен при требованиях команды и эксплуатации | Добавляет второй язык и требует отдельно обосновать сопровождение |

**Предварительная рекомендация для обсуждения — NestJS на TypeScript:** полный объём соцсети содержит много доменов с перекрёстными зависимостями; стандартная организация модулей полезна при последовательной реализации. Fastify остаётся равноправной альтернативой, если предпочтительны явные функции и меньше framework-абстракций. Это оценка требований проекта, не утверждение о производительности и не выбранная зависимость.

Для постоянных связанных данных предлагается PostgreSQL. Выбор ORM и мигратора вынести в следующий небольшой проектный шаг: проверить транзакции, ограничения, индексы и удобство интеграционных тестов. Изображения хранятся вне таблиц БД; в базе — владелец, ключ, статус и метаданные. Площадка хранения и рабочие версии пакетов пока не выбираются.

## Границы модулей

| Модуль | Ответственность |
| --- | --- |
| identity | Учётная запись, подтверждение email, пароль, OAuth-идентичности |
| sessions/access | Сессии устройств, отзыв, роли, текущий субъект и проверка доступа |
| profiles | Публичные и личные поля профиля, ссылки на аватар |
| media | Загрузка, проверка, обработка, владение и очистка файлов |
| posts | Публикации, видимость, редактирование и удаление |
| social | Подписки на авторов, лайки, комментарии и сохранённое |
| feed/search | Выборки доступного контента и поиск с правилами пагинации |
| messaging | Диалоги, участники, сообщения и состояния доставки |
| notifications | История уведомлений, read-state и доставка событий |
| billing | Платежи, подписки, сверка и обработка webhook |
| moderation | Блокировки, действия администратора и аудит |
| integrations | Адаптеры почты, перевода, OAuth и платёжных провайдеров |

Это логическая карта: не создавать пустые каталоги всех модулей заранее. Транспорт вызывает сценарий; сценарий проверяет права и меняет состояние через слой данных. Обработчики HTTP/Socket не дублируют бизнес-правила. Модерация обращается к тем же операциям аккаунтов/контента; billing сохраняет уникальность внешних событий в БД. Точные транзакционные границы и доставка событий проектируются отдельно.

## Подключение интерфейсов

Существующий web BFF сохранить на этапе подключения, пока отдельно не согласована замена его авторизации. Только backend получает доступ к БД и определяет права; BFF отвечает за адаптацию запросов и cookies. Сохранение маршрутов не означает сохранения небезопасных токен-мостов или общего refreshPromise.

Для admin есть два варианта: временная совместимость с пятью существующими GraphQL-операциями либо переход на REST вместе с новой сессией. Решение зависит от цены миграции: не вводить GraphQL только ради заглушек будущих экранов. Форматы ошибок и пагинации нового API должны быть стабильными; адаптация старых потребителей выполняется отдельными PR. Сессии, CSRF и socket authentication будут описаны до реализации auth.

## Что должно подтвердить реализацию

Каждый следующий PR имеет одну цель и отдельную проверку. Каркас проверяет запуск, конфигурацию и health; БД — миграции на чистой базе и ограничения; auth — положительные и отрицательные сценарии сессий; продуктовые модули — права владельца, ошибки и повторные запросы. После появления сервера CI дополняется typecheck, тестами и проверками БД. Возможность собрать UI не заменяет эти проверки.

## Следующие решения

1. Согласовать отдельный модульный монолит и выбрать NestJS или Fastify.
2. Описать модель сессий, ролей, OAuth и подключение admin.
3. Выбрать слой БД и описать первые таблицы/миграции.
4. Зафиксировать контракт базовых сценариев и план локального окружения.
5. Реализовать каркас сервера отдельным PR; БД и auth добавлять следующими небольшими изменениями.
