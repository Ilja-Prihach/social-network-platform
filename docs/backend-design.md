# Целевая архитектура бэкенда

Статус: базовое решение согласовано владельцем. Реализация ещё не начата. Основание — [функции](feature-inventory.md) и [контракты потребителей](api-inventory.md).

## Выбранная основа

Отдельное приложение `backend/` в текущем npm-монорепозитории: модульный монолит на NestJS и TypeScript, PostgreSQL и Drizzle. Один сервер обслуживает web и admin; общая база хранит связанные данные. NestJS задаёт организацию модулей и зависимостей, Drizzle — типизированную работу с SQL. SQL-миграции проверяются в PR и на тестовой PostgreSQL.

Отдельный процесс позволяет развивать общие бизнес-правила независимо от Next.js. Модульный монолит сохраняет простые вызовы и транзакции между доменами. Разделение на сервисы сейчас добавило бы инфраструктуру и распределённую согласованность без подтверждённой потребности. Drizzle выбран для явных запросов и просмотра SQL-миграций; это требует знания SQL и проверки индексов и планов запросов.

## Структура

```text
backend/
  src/
    app/              Подключение модулей
    config/           Проверка окружения
    modules/          Бизнес-модули
    infrastructure/   База, файлы, почта, фоновые задания
    shared/           Общие технические типы и ошибки
    main.ts           Запуск и корректная остановка
  migrations/         SQL-миграции
  tests/              Интеграционные и сквозные проверки
```

Модуль содержит контроллеры, сервисы, репозитории и схемы входных/выходных данных; тесты бизнес-правил располагаются рядом с кодом. Каталоги создаются по мере реализации. Общий пул соединений предоставляется через NestJS; репозитории получают явную транзакцию для операций, которые должны завершиться атомарно.

## Карта ответственности для детализации

| Область | Ответственность |
| --- | --- |
| identity / sessions | Аккаунт, пароль, email, OAuth, сессии устройств и отзыв доступа |
| profiles / media | Профиль, аватары, загрузки, проверка и очистка файлов |
| posts / relationships / interactions | Публикации, подписки на авторов, лайки, комментарии и сохранённое |
| discovery | Ленты и поиск доступного контента |
| messaging / notifications | Диалоги и сообщения; история и доставка уведомлений |
| billing | Тарифы, подписки, платежи и события провайдеров |
| moderation | Блокировки, административные действия и аудит |
| translation | Перевод постов и ограничения провайдера |

Модули изменяют свои данные; межмодульные операции проходят через явные публичные интерфейсы. HTTP и realtime вызывают общие бизнес-сценарии. Для общих выборок ленты допускаются специально определённые запросы чтения; они не дают модулю права произвольно изменять чужие таблицы. Точные транзакционные границы уточняются при проектировании сценариев.

Внешние вызовы почты и платежей не выполняются внутри длительных транзакций БД. Механизм надёжных фоновых заданий, событий и повторных попыток выбирается отдельно. Файлы хранятся вне таблиц PostgreSQL, в базе — метаданные и права владения; провайдер хранения пока не выбран.

## Следующие решения в разговоре с владельцем

1. Схема identity, sessions и profiles; механизм сессий и роли.
2. ID сущностей, ограничения, индексы, сроки хранения и удаление данных.
3. Контракты web BFF и admin: совместимость, REST/GraphQL, cookies и realtime.
4. Локальное окружение и тесты; конкретные совместимые версии пакетов.
5. Небольшой PR каркаса сервера, затем отдельные PR базы и сценариев auth.

UUID, серверные сессии и названия будущих таблиц пока являются предложениями. Их обсуждение не означает утверждения. Сначала выбираем решение в разговоре, затем фиксируем в PR.

Правила выпусков и откатов: [versioning.md](versioning.md).
