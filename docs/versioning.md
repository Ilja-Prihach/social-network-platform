# Версии и откаты

Статус: согласовано владельцем. На старте web, admin и backend входят в один выпуск продукта. Каждый выпуск указывает на один коммит монорепозитория; версии отдельных npm-пакетов не используются как признак развёрнутого выпуска.

## Выпуски

- Первый согласованный и проверенный выпуск получает `0.1.0` и Git-тег `v0.1.0`.
- Исправления без изменения совместимости — patch, например `0.1.1`.
- Следующий законченный этап или несовместимое изменение до версии 1.0 — minor, например `0.2.0`, с явным описанием перехода.
- После 1.0 несовместимые изменения требуют major; новые совместимые возможности — minor; исправления — patch.
- Релиз объединяет проверенный набор PR; каждый PR не требует новой версии.
- Тег выпуска неизменяем: ошибку исправляем новым выпуском. Тег создаётся после merge и успешных проверок нужного коммита по решению владельца.

`CHANGELOG.md` хранит краткие изменения, исправления, миграции и требования совместимости. До первого выпуска записи находятся в разделе «Не выпущено». Сейчас релиз и тег не создаются.

## Откат кода

Ошибка в Git отменяется через revert в отдельной ветке и PR. Историю main не переписываем. При настройке деплоя сохраняем неизменяемые сборки с версией и полным SHA коммита. Возможность возврата предыдущего артефакта проверяется вместе с его совместимостью с текущей базой, конфигурацией и внешними интеграциями. CD пока не настроен.

## База данных

Возврат сборки не отменяет SQL-миграции и не восстанавливает удалённые данные. Миграции применяются контролируемым шагом; уже применённые файлы не переписываются.

Изменения делаем постепенно: добавляем новую структуру, выпускаем совместимый код, переносим данные, переключаем чтение/запись и только последующим выпуском удаляем старую структуру. Перед удалением проверяем, что предыдущая сборка больше не нужна и все экземпляры приложения используют новую схему.

Для каждого релиза с миграцией указываем допустимую предыдущую версию приложения и план восстановления. Перед опасными изменениями нужны резервная копия и проверка восстановления. Восстановление базы может потерять записи после точки копирования и требует отдельного решения; оно не равно безопасному откату приложения. Автоматические destructive down-миграции при ошибке приложения не выполняем. При возможности исправляем схему новой миграцией вперёд.
